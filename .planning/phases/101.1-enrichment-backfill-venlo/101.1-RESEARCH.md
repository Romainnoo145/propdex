# Phase 101.1: Enrichment Backfill Venlo - Research

**Researched:** 2026-03-11
**Domain:** CLI batch enrichment tool + score re-computation
**Confidence:** HIGH

## Summary

Phase 101.1 creates a standalone CLI backfill tool that retroactively fetches all 10 Phase 99 enrichment data sources for existing Venlo parcels, then re-scores them with the v3.0 engine. This is needed because the existing 21 Venlo wijk scans were run BEFORE Phase 99 enrichment was integrated, so `scan_results.flags` is missing the environmental/address-based enrichment keys (natura2000, overstromingsrisico, geluid, luchtkwaliteit, energielabel, woz, vergunningen, funderingsrisico). Bodem and bodemtype may already be partially present from Phase 3b of the scan pipeline.

The tool follows the established backfill pattern from `backfill_scan_scores_v3.py` and `backfill_3dbag.py`: paginate through scan_results in batches, load related parcel_cache data, call external APIs with deduplication, merge results into `scan_results.flags`, and re-score. The primary storage target is `scan_results.flags` JSONB (matching the scan pipeline), NOT `parcel_cache.enrichment_data` (which is for on-demand Tier 2 caching of SRU vergunningen on panel open).

**Primary recommendation:** Build a single `backfill_enrichment.py` CLI tool that processes parcels in wijk-batches (matching scan boundaries), runs coordinate-based enrichment first (6 sources via centroids), then address-based enrichment (4 sources via VBO/nummeraanduiding/postcode), merges into `scan_results.flags`, and finally re-scores with `compute_score_v3()`.

## Architecture Patterns

### Recommended Project Structure
```
backend/app/tools/
    backfill_enrichment.py      # NEW: main CLI backfill tool
```

Single file, following `backfill_3dbag.py` and `backfill_scan_scores_v3.py` patterns.

### Pattern 1: Wijk-Batch Processing
**What:** Process parcels grouped by scan_id (wijk), not globally. Each wijk scan has ~3k-8k parcels.
**When to use:** Always -- matches how data was originally collected and how deduplication works.
**Why:** Coordinate deduplication (50m rounding) works best within a geographic cluster. Processing 137k parcels globally would create a massive dedup dictionary. Wijk batches keep memory bounded.

### Pattern 2: Two-Phase Enrichment (Coordinate then Address)
**What:** First run coordinate-based enrichment (natura2000, overstromingsrisico, geluid, luchtkwaliteit, bodem, bodemtype) using centroids from parcel_cache.geometry. Then run address-based enrichment (energielabel, woz, vergunningen, funderingsrisico) using resolved VBO/nummeraanduiding/postcode from parcel_cache.address.
**When to use:** Always -- mirrors Phase 3b + Phase 5b of area_scan.py.

### Pattern 3: Flags Merge, Not Replace
**What:** Read existing `scan_results.flags` dict, merge new enrichment keys, write back. Never overwrite existing keys like vacancy_signal, building_metrics.
**When to use:** Always -- scan_results.flags contains vacancy, market signals, building metrics from original scan.

### Pattern 4: Skip-Already-Enriched
**What:** Before fetching, check if the enrichment keys already exist in flags. Skip parcels that already have all 10 enrichment keys populated.
**When to use:** For idempotency -- allows re-running the tool safely after partial completion.

### Anti-Patterns to Avoid
- **Writing to parcel_cache.enrichment_data instead of scan_results.flags:** The scan pipeline stores enrichment in flags. The on-demand path (parcel_cache.enrichment_data) is only for SRU vergunningen when user opens a parcel detail. Mixing the two creates data duplication.
- **Processing all 137k parcels in one batch:** Memory explosion. Use wijk-batch (scan_id grouped) processing.
- **Ignoring rate limiters:** The government API clients have built-in `APIRateLimiter` instances. But the backfill tool creates raw Semaphores in `scan_enrichment.py` functions. For a backfill of 137k parcels, reduce concurrency further or add inter-batch delays.
- **Re-resolving addresses:** Addresses are already resolved and stored in `parcel_cache.address`. Extract postcode from there, don't re-call PDOK Locatieserver.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Coordinate enrichment | Custom API fetch loops | `batch_fetch_bodem_data()` + `batch_fetch_environmental_data()` from `scan_enrichment.py` | Already handles dedup, error isolation, result fan-out |
| Postcode enrichment | Custom SRU/funder loops | `batch_fetch_postcode_enrichment()` from `scan_enrichment.py` | Postcode dedup + parallel SRU + funderingsrisico |
| Address enrichment | Custom EP/WOZ loops | `batch_fetch_address_enrichment()` from `scan_enrichment.py` | VBO/nummeraanduiding dedup + parallel EP + WOZ |
| Score recomputation | Custom score logic | `compute_score_v3()` from `score_v3.py` | Already handles missing data, weight redistribution |
| Centroid extraction | Custom geometry parsing | `geoalchemy2.shape.to_shape(geom).centroid` | Standard PostGIS/Shapely pattern |

**Key insight:** ALL enrichment functions already exist in `scan_enrichment.py`. The backfill tool is purely an orchestrator that feeds data from the database into these existing functions and writes results back.

## Common Pitfalls

### Pitfall 1: Rate Limiting Exhaustion
**What goes wrong:** 137k parcels with ~50m dedup still means ~5k-10k unique coordinate queries per source, plus ~3k unique postcodes. At 500/hour rate limits (EP-Online, WOZ, SRU), this takes 6+ hours per source.
**Why it happens:** Rate limiters are designed for single-wijk scans (~500 parcels), not bulk backfill.
**How to avoid:** Process wijk-by-wijk with inter-wijk pauses (5-10 seconds). Use existing Semaphore-based concurrency in scan_enrichment.py functions (3-5 concurrent per source). Log progress per wijk. Allow resuming from a specific scan_id.
**Warning signs:** `aiolimiter` blocking for long periods, API 429 responses.

### Pitfall 2: VBO/Nummeraanduiding IDs Not Available
**What goes wrong:** EP-Online needs VBO ID, WOZ needs nummeraanduiding ID. These are resolved during Phase 5 of area_scan.py via PDOK Locatieserver reverse geocoding. But they are NOT stored in parcel_cache -- only the final address string is stored.
**Why it happens:** The scan pipeline resolves addresses in-memory and passes them to Phase 5b enrichment, but only persists `parcel_cache.address`. The VBO ID and nummeraanduiding ID are discarded after the scan.
**How to avoid:** For the backfill, re-resolve addresses using the existing reverse geocode function `reverse_geocode_rd_point_full()` from `parcel_addressing.py`. This returns `AddressResolution(address, postcode, nummeraanduiding_id, vbo_id)`. Extract centroids from parcel_cache.geometry and batch-resolve.
**Warning signs:** Empty energielabel/woz results because VBO/nummeraanduiding IDs are missing.

### Pitfall 3: Postcode Extraction from Address String
**What goes wrong:** For funderingsrisico and SRU vergunningen, we need PC6 postcode. The parcel_cache.address field contains full address strings like "Kaldenkerkerweg 123, 5913 AB Venlo".
**Why it happens:** Postcode is embedded in address, not a separate column.
**How to avoid:** Use regex extraction (already exists in scans/router.py): `re.search(r'\b(\d{4}\s?[A-Z]{2})\b', address)`. Or better: use AddressResolution.postcode from re-resolved addresses (Pitfall 2 solution).

### Pitfall 4: SQLAlchemy Session Management
**What goes wrong:** Long-running backfill with many flushes can cause session bloat or "transaction already begun" errors.
**Why it happens:** Propdex uses direct db.add()/flush()/commit() pattern, NOT `async with db.begin()`.
**How to avoid:** Commit after each wijk batch. Use `async_session_factory()` with fresh sessions per batch if needed. Follow `backfill_scan_scores_v3.py` pattern exactly.

### Pitfall 5: EP-Online Not Configured
**What goes wrong:** `ep_online_client.get_by_vbo_id()` returns None when `EP_ONLINE_API_KEY` is not set in `.env`.
**Why it happens:** EP-Online requires an API key, unlike the public APIs.
**How to avoid:** Check `settings.EP_ONLINE_API_KEY` at startup. Warn user if not configured. Proceed with other sources -- energielabel enrichment is non-fatal.

### Pitfall 6: Existing Bodem Data
**What goes wrong:** Bodem and bodemtype may already be present in flags from Phase 3b of original scans (those were integrated before Phase 99 address enrichment).
**Why it happens:** Phase 99 was rolled out incrementally -- coordinate-based enrichment (bodem) was added first.
**How to avoid:** Check for existing keys before overwriting. Skip bodem/bodemtype if already present (skip-already-enriched pattern).

## Code Examples

### Centroid Extraction from ParcelCache
```python
# Source: established pattern in backfill_3dbag.py + geoalchemy2
from geoalchemy2.shape import to_shape

def extract_centroid(parcel: ParcelCache) -> tuple[float, float] | None:
    """Extract RD centroid coordinates from parcel geometry."""
    if parcel.geometry is None:
        return None
    shape_obj = to_shape(parcel.geometry)
    centroid = shape_obj.centroid
    return (centroid.x, centroid.y)
```

### Flags Merge Pattern
```python
# Source: area_scan.py Phase 5b merge pattern (lines 795-813)
existing_flags = dict(sr.flags) if sr.flags else {}

# Merge coordinate-based enrichment
for key in ("natura2000", "overstromingsrisico", "geluid", "luchtkwaliteit", "bodem", "bodemtype"):
    if key not in existing_flags and env_data.get(key):
        existing_flags[key] = env_data[key]

# Merge address-based enrichment
if "vergunningen" not in existing_flags and pc_data.get("vergunningen"):
    existing_flags["vergunningen"] = pc_data["vergunningen"]
if "funderingsrisico" not in existing_flags and pc_data.get("funderingsrisico"):
    existing_flags["funderingsrisico"] = pc_data["funderingsrisico"]
if "energielabel" not in existing_flags and addr_data.get("energielabel"):
    existing_flags["energielabel"] = addr_data["energielabel"]
if "woz" not in existing_flags and addr_data.get("woz"):
    existing_flags["woz"] = addr_data["woz"]

sr.flags = existing_flags
session.add(sr)
```

## Open Questions

1. **EP-Online API Key availability**
   - What we know: EP-Online requires `EP_ONLINE_API_KEY` in backend/.env
   - What's unclear: Whether the key is currently configured for this environment
   - Recommendation: Check at tool startup, warn if missing, proceed without energielabel

2. **Estimated runtime**
   - What we know: 21 wijken, ~137k parcels, ~51k with addresses. Rate limits: 500/hr for EP-Online, WOZ, SRU.
   - What's unclear: Actual dedup ratios for Venlo (how many unique postcodes, unique 50m-rounded coords)
   - Recommendation: Estimate ~2-4 hours for coordinate-based (high dedup ratio), ~4-8 hours for address-based (500/hr rate limit with ~30k VBO IDs). Add --resume flag for interrupted runs.

3. **Re-resolution volume for VBO/nummeraanduiding IDs**
   - What we know: ~51k parcels have addresses. PDOK Locatieserver rate limit is 50,000/hr (generous).
   - What's unclear: Whether we can batch-resolve more efficiently or if we need per-parcel reverse geocoding
   - Recommendation: Use PDOK Locatieserver reverse geocode with 10 concurrent (matching existing limiter). ~51k requests at 10 concurrent = ~85 minutes.
