# Phase 77.1: UX Architectuur & Component Refactor - Research

**Researched:** 2026-03-07
**Domain:** React component architecture, tabbed UI patterns, progressive disclosure
**Confidence:** HIGH

## Summary

Phase 77.1 is a purely structural frontend refactor. It transforms three existing views (WijkDetailView, WijkMapPanel, ParcelDetailModal) from flat scrolling layouts into tabbed/collapsible containers that subsequent data phases (78-84) can slot content into without touching the container code.

The existing codebase already uses React 19, TanStack Router, TanStack Query, Tailwind CSS, Lucide icons, and class-variance-authority. No new dependencies are needed. The work is entirely compositional: building tab and collapsible section containers from Tailwind primitives, then reorganizing existing content into those containers.

The key architectural decision is using a composition/slot pattern (React `children` + typed props) rather than a registry/plugin pattern. This aligns with the codebase convention of explicit component trees and keeps the planner's task simple: each future data phase adds a card component and inserts it as a child of the appropriate tab.

**Primary recommendation:** Build a `TabContainer` primitive and a `CollapsibleSection` primitive, then refactor WijkDetailView, WijkMapPanel, and ParcelDetailModal to use them. Keep all components under 300 LOC per the project rule.

### Pattern 1: TabContainer Primitive
**What:** A controlled tab component that renders tab headers and shows the active panel.
**When to use:** Any view that needs tabbed navigation (WijkDetailView, WijkMapPanel).
**Design:**
```typescript
// TabContainer.tsx — under 100 LOC
interface Tab {
  id: string
  label: string
  icon?: React.ReactNode
  badge?: string | number  // e.g., count indicator
}

interface TabContainerProps {
  tabs: Tab[]
  activeTab: string
  onTabChange: (tabId: string) => void
  children: React.ReactNode  // Active panel content
  variant?: 'default' | 'compact'  // compact = smaller text/padding for map panel
  className?: string
}

export function TabContainer({ tabs, activeTab, onTabChange, children, variant = 'default', className }: TabContainerProps) {
  return (
    <div className={className}>
      {/* Tab bar */}
      <div className="flex border-b border-overlay/5 overflow-x-auto scrollbar-hidden">
        {tabs.map((tab) => (
          <button
            key={tab.id}
            onClick={() => onTabChange(tab.id)}
            className={clsx(
              'shrink-0 px-4 py-2.5 text-xs font-medium transition-colors border-b-2',
              variant === 'compact' && 'px-3 py-2 text-[11px]',
              activeTab === tab.id
                ? 'border-amber-accent text-amber-accent'
                : 'border-transparent text-grey-400 hover:text-grey-200'
            )}
          >
            <span className="flex items-center gap-1.5">
              {tab.icon}
              {tab.label}
              {tab.badge != null && (
                <span className="rounded-full bg-grey-800 px-1.5 text-[10px] text-grey-400">
                  {tab.badge}
                </span>
              )}
            </span>
          </button>
        ))}
      </div>
      {/* Active tab content */}
      <div>{children}</div>
    </div>
  )
}
```

### Pattern 2: CollapsibleSection Primitive
**What:** A section with a header that toggles content visibility on click.
**When to use:** ParcelDetailModal grouped sections, LocationScoreCard dimension details.
**Design:**
```typescript
// CollapsibleSection.tsx — under 80 LOC
interface CollapsibleSectionProps {
  title: string
  icon?: React.ReactNode
  defaultOpen?: boolean
  badge?: React.ReactNode       // e.g., traffic-light indicator
  children: React.ReactNode
  className?: string
}

export function CollapsibleSection({
  title, icon, defaultOpen = true, badge, children, className
}: CollapsibleSectionProps) {
  const [isOpen, setIsOpen] = useState(defaultOpen)

  return (
    <section className={clsx('rounded-xl border border-overlay/5 bg-grey-900 overflow-hidden', className)}>
      <button
        type="button"
        onClick={() => setIsOpen(!isOpen)}
        className="flex w-full items-center gap-2 border-b border-overlay/5 px-4 py-2.5"
      >
        {icon}
        <span className="text-xs font-medium uppercase tracking-wide text-amber-accent/70">
          {title}
        </span>
        {badge && <span className="ml-auto mr-2">{badge}</span>}
        <ChevronDown className={clsx(
          'w-3.5 h-3.5 text-grey-500 transition-transform ml-auto',
          isOpen && 'rotate-180'
        )} />
      </button>
      {isOpen && <div className="p-4">{children}</div>}
    </section>
  )
}
```

### Pattern 4: Composition / Slot Pattern
**What:** Parent containers accept `children` or typed render props. Data phases insert their cards as direct children.
**Why:** Explicit, type-safe, no runtime registry overhead. Follows existing codebase patterns (MapPanelShell, Modal all use children).
**Example future usage (Phase 78):**
```typescript
// In WijkDetailView, inside "Demografie & Inkomen" tab:
<DemografieTab>
  <LeeftijdsverdelingCard metrics={metrics} />
  <HuishoudensCard metrics={metrics} />
  <InkomensCard metrics={metrics} />
</DemografieTab>
```

### Anti-Patterns to Avoid
- **Monolith components:** ParcelDetailModal is 694 lines -- must decompose into sub-components that each stay under 300 LOC
- **Prop drilling for tab state:** Use local `useState` in the container -- tabs don't need to be in URL state or global context
- **Conditional rendering chaos:** Use TabContainer's `activeTab` rather than a chain of `{tab === 'x' && ...}` blocks
- **Building a full tab library:** No need for headless-ui or radix-ui tabs -- a simple 60-line component suffices

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Icon system | Custom SVG components | lucide-react (already installed) | Consistent, tree-shakeable |
| Class merging | String concatenation | clsx + tailwind-merge (already installed) | Handles Tailwind conflicts |
| Component variants | Manual className logic | class-variance-authority (already installed) | Type-safe variant maps |

**Key insight:** All UI infrastructure is already in place. This phase only builds two lightweight primitives (TabContainer, CollapsibleSection) and restructures existing content.

## Common Pitfalls

### Pitfall 1: Breaking Existing Data Flow
**What goes wrong:** Refactoring ParcelDetailModal into sub-components but losing the enrichment query, parcelChanges query, or report generation handler.
**Why it happens:** Data hooks are called at the top of ParcelDetailModal and results passed down. Moving sections to sub-components risks disconnecting these.
**How to avoid:** Keep all hooks in the parent ParcelDetailModal and pass data as props to extracted section components. Do NOT move hooks into child components -- this avoids re-fetching and maintains the single-fetch pattern.
**Warning signs:** Multiple network requests for the same data, enrichment data not appearing in sub-sections.

### Pitfall 2: WijkMapPanel vs WijkDetailView Tab Mismatch
**What goes wrong:** WijkMapPanel and WijkDetailView have different tab sets, but the requirement says WijkMapPanel should use "the same tab structure."
**Why it happens:** WijkMapPanel is a compact side panel (384px wide) with different data availability (it receives `latestScan` directly, not from hooks).
**How to avoid:** Use the same `TabContainer` with `variant="compact"` for WijkMapPanel. Use identical tab IDs. Allow individual tabs to show "scan first" placeholders when data is unavailable.
**Warning signs:** Users seeing different navigation between map panel and project detail view.

### Pitfall 3: ParcelDetailModal Dual Presentation
**What goes wrong:** ParcelDetailModal supports both `modal` and `map-panel` presentations. Refactoring the content can break one of the two modes.
**Why it happens:** The `content` JSX is shared between Modal and MapPanelShell wrappers.
**How to avoid:** Keep the dual-presentation pattern. Extract content into named section components, but keep the presentation switch in the parent.
**Warning signs:** Map panel version looks wrong, or modal version loses scroll behavior.

### Pitfall 4: Over 300 LOC Limit
**What goes wrong:** After adding tabs to WijkDetailView, the component exceeds the 300-line project limit.
**Why it happens:** Tab content for 5 tabs plus the scorecard shell adds up.
**How to avoid:** Each tab's content should be a separate component file. WijkDetailView itself should only handle tab state and render TabContainer with the active tab's component.
**Warning signs:** Any single file exceeding 300 lines during implementation.

### Pitfall 5: CSS Conflicts with Existing Styles
**What goes wrong:** New tab border-bottom styling conflicts with existing `border-overlay/5` card patterns.
**Why it happens:** The project uses CSS variables extensively. New primitives must follow the same token system.
**How to avoid:** Use existing color tokens (`amber-accent`, `grey-*`, `overlay`) -- never hardcode hex colors. Use `border-overlay/5` for subtle borders, `border-amber-accent` for active states.
**Warning signs:** Visual inconsistency between new tabs and existing card components.

## Open Questions

1. **Tab persistence across navigation**
   - What we know: WijkDetailView is rendered inside the project drilldown. Tab state is local (useState).
   - What's unclear: Should the active tab persist when switching between wijken in the same gemeente?
   - Recommendation: Use local state (simplest). Each wijk opens on "Overzicht" tab. No URL state needed for tabs.

2. **Demografie & Leefbaarheid tabs -- empty state**
   - What we know: Phase 78-80 will populate these tabs. Until then, they'll be empty.
   - What's unclear: Should we show placeholder text, or hide the tabs entirely until data phases ship?
   - Recommendation: Show all tabs immediately with "Binnenkort beschikbaar" placeholder. This communicates the product direction and avoids layout shifts when data phases ship.
