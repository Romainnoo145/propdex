# Phase 76.1: Map Toggle State Machine - Research

**Researched:** 2026-03-07
**Domain:** React state management, MapLibre GL JS layer orchestration, UI state machines
**Confidence:** HIGH (all findings from direct codebase inspection)

## Summary

Phase 76.1 addresses accumulated technical debt in the map toggle system — specifically the split-brain problem where layer visibility state lives in two different places simultaneously: `LayerToggle.tsx` (local React state + localStorage writes) and `map.tsx` (a parallel mirror of the same state via callbacks). This dual-state model has already produced concrete bugs (uncommitted changes from 2026-03-07 session, `NOT YET COMMITTED` note in MEMORY.md), and will become increasingly painful as Phase 77 adds more map context interactions.

The core issue is architectural: `LayerToggle` is simultaneously a UI component AND a state authority. It owns the layer boolean states, triggers map side-effects via callbacks, and reads/writes localStorage — all without the parent (`map.tsx`) having a single source of truth. The parent compensates by maintaining its own parallel booleans (`showGemeentenLayer`, `showBestemmingsplan`, `isParcelsVisible`) that must be kept in sync via the callback chain.

The recommended approach is to lift all toggle state into `map.tsx` as a single `MapLayerState` object (or a `useReducer` with well-typed actions), and reduce `LayerToggle` to a pure presentational component that receives state + dispatch callbacks. This is a pure frontend refactor with no backend changes.

**Primary recommendation:** Extract a `useMapLayerState` hook that owns toggle state and localStorage persistence, then thread it into `LayerToggle` as controlled props. The map click priority logic (`parcelModeActive`) must be derived from this single source — not from stale closures.

### Pattern 1: Lift State into `useMapLayerState` Hook

**What:** Extract all toggle booleans and their persistence logic into a custom hook in `lib/map/useMapLayerState.ts`. The hook returns the full state object plus typed setters.

**When to use:** Any time a component is both a state authority and a presenter — classic "lift state" refactor.

**Example:**
```typescript
// lib/map/useMapLayerState.ts
export interface MapLayerState {
  basemap: BaseMapLayerId
  showParcels: boolean
  showGemeenten: boolean
  showBestemmingsplan: boolean
  activeParcelOverlay: ParcelOverlayLayerId | null
}

export function useMapLayerState() {
  const [state, setState] = useState<MapLayerState>(() => readPersistedMapLayerState())

  // Persist on every change
  useEffect(() => {
    writePersistedMapLayerState(state)
  }, [state])

  const setBasemap = useCallback((v: BaseMapLayerId) =>
    setState(s => ({ ...s, basemap: v })), [])

  const setParcels = useCallback((v: boolean) =>
    setState(s => ({ ...s, showParcels: v })), [])

  // ... etc.

  return { state, setBasemap, setParcels, ... }
}
```

### Pattern 2: `LayerToggle` as Pure Controlled Component

**What:** Remove all internal state from `LayerToggle`. It receives current values via props and calls handlers when user interacts. No `useState` inside.

**When to use:** Any component that currently has internal state that duplicates parent state.

**Example:**
```typescript
// LayerToggle.tsx — controlled
interface LayerToggleProps {
  basemap: BaseMapLayerId
  showParcels: boolean
  showGemeenten: boolean
  showBestemmingsplan: boolean
  onBasemapChange: (v: BaseMapLayerId) => void
  onParcelsToggle: () => void
  onGemeentenToggle: () => void
  onBestemmingsplanToggle: () => void
  // Map readiness guard stays inside component
  mapRef: React.RefObject<maplibregl.Map | null>
  mapReady?: boolean
}
```

### Pattern 3: Derive `parcelModeActive` from State (Fix Stale Closure)

**What:** The click handler closure captures `isParcelsVisible` at registration time. Fix by using a `useRef` that is always updated with the latest value — or better, by computing `parcelModeActive` fresh from the ref.

**Current (broken):**
```typescript
// line 1193 — stale closure risk
const parcelModeActive = isParcelsVisible || !!activeScanIdRef.current
```

**Fixed (derive from ref, same pattern as `activeScanIdRef`):**
```typescript
const isParcelsVisibleRef = useRef(isParcelsVisible)
isParcelsVisibleRef.current = isParcelsVisible  // keep in sync, same pattern already used

// inside click handler (stable closure):
const parcelModeActive = isParcelsVisibleRef.current || !!activeScanIdRef.current
```

Or alternatively — simplify by deriving from the lifted state via a ref.

### Anti-Patterns to Avoid

- **Duplicating state**: Never have `showParcels` in both `LayerToggle` and `map.tsx`. Pick one owner.
- **Callback-driven sync**: Don't use callbacks to keep state in sync — lift state instead, pass down values.
- **Map side-effects in `LayerToggle`**: `LayerToggle` should call `setParcelBoundariesVisibility(map, ...)` — but the caller decides when. The map effect should live in `map.tsx` in a `useEffect` that watches the state.
- **Auto-enabling parcels from `LayerToggle`**: The `autoEnableParcelsKey` prop pattern (current) causes `LayerToggle` to imperatively call map APIs. Move that logic into `map.tsx` where it belongs.

## Common Pitfalls

### Pitfall 1: Stale Closure in Map Event Handlers

**What goes wrong:** Map event handlers (click, mousemove) are registered once via `map.on(...)` and hold a closure over their parent scope. If the closure captures a boolean like `isParcelsVisible` instead of a ref, the handler sees the value from when it was registered — not the current value.

**Why it happens:** React re-renders don't re-register map event handlers (they're imperative). Only code in the effect cleanup/re-register cycle can update what the handler sees.

**How to avoid:** For all live state consumed inside map handlers, use the `useRef` pattern already established in the codebase:
```typescript
const isParcelsVisibleRef = useRef(isParcelsVisible)
isParcelsVisibleRef.current = isParcelsVisible  // run every render — cheap
// Then in handler: use isParcelsVisibleRef.current
```

**Warning signs:** Handler uses a boolean state directly (not via ref), and you see toggling work on first click but not subsequent ones.

### Pitfall 2: `layerToggle` `useEffect` Dependency Explosion

**What goes wrong:** `LayerToggle.tsx` has a `useEffect` (lines 154-198) with 18 dependencies. Any of those can trigger it. After lifting state, the effect must be reconstructed — missing a dep will cause bugs, including too many deps will cause infinite loops.

**Why it happens:** The effect was written to work around the split-state model. Once state is lifted, the effect simplifies to a one-time map init.

**How to avoid:** After lifting state, the `didInitSyncRef` init effect in `LayerToggle` becomes a simple setup call: "add parcel source if missing, set initial visibility." Its deps should be just `[mapReady]` and a stable ref.

### Pitfall 3: `autoEnableParcelsKey` Coupling

**What goes wrong:** `LayerToggle` currently reacts to `autoEnableParcelsKey` prop by imperatively calling `setParcelBoundariesVisibility(map, true)` and `setShowParcels(true)` — driving state changes into its sibling. This is prop-driven imperative side-effecting.

**Why it happens:** Before the lift, `LayerToggle` owned `showParcels`, so it needed to hear about external triggers. After the lift, external triggers can update state directly in `map.tsx` — no prop needed.

**How to avoid:** Move `autoEnableParcelsKey` logic entirely into `map.tsx`. When the key changes, set `showParcels: true` in the lifted state. Remove the prop from `LayerToggle`.

### Pitfall 4: `LayerToggle` `showXToggle` Prop Explosion

**What goes wrong:** `LayerToggle` currently receives 14+ props (7 toggle handlers + 7 visibility flags like `showScoreToggle`, `showBuiltStatusToggle`, etc.) — all set to `false` in the current call site (lines 2064-2073 of map.tsx). These dead props create interface noise.

**Why it happens:** The toggle grew organically as features were added. Props were never pruned when features were removed from the toggle bar.

**How to avoid:** Audit every `showXToggle` prop. If the map.tsx call site passes `false` unconditionally, remove both the prop and the dead conditional in `LayerToggle`. A smaller interface = fewer bugs.

## Open Questions

1. **Should localStorage persistence be re-enabled?**
   - What we know: It was deliberately disabled ("map always starts clean") — lines 67-76 of layers.ts
   - What's unclear: Was this a product decision or technical workaround? The MEMORY.md note "stubbed localStorage persistence" suggests it was deferred.
   - Recommendation: Planner should include a task to re-enable localStorage persistence as part of this phase, since the hook refactor makes it trivially easy. But treat it as optional scope.

2. **Should `activeParcelOverlay` (score/built/report/vacancy/capacity) be kept in the state machine?**
   - What we know: These 5 overlay toggles are mutually exclusive (radio group pattern). Currently modeled as 5 separate booleans.
   - What's unclear: Are any of the overlay toggle buttons still shown? In map.tsx, all `showXToggle` props are `false`. The overlays are set via `setParcelOverlayMode()` internally.
   - Recommendation: Collapse the 5 booleans into `activeParcelOverlay: ParcelOverlayLayerId | null`. This is already the type in `PersistedMapLayerState` — the implementation just hasn't caught up.

3. **Should `autoEnableParcelsKey` be removed entirely after lift?**
   - What we know: It exists to tell `LayerToggle` to force-enable parcels from outside (URL navigation / address search flows).
   - What's unclear: After lifting state, `map.tsx` can directly set `showParcels: true` when these flows trigger — no key needed.
   - Recommendation: Yes, remove after lift. Replace with direct state update in the map.tsx effects that currently set `autoEnableParcelsKey`.

4. **What are the exact bugs that triggered this phase insertion?**
