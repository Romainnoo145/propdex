# Phase 93.1: Potentie Dashboard - Research

**Researched:** 2026-03-11
**Domain:** Frontend — React component redesign (no backend changes)
**Confidence:** HIGH

## Summary

Phase 93.1 replaces the existing `PotentieLayer.tsx` (a scrollable BentoPod list) with a no-scroll investor dashboard. The current PotentieLayer renders 5 stacked BentoPods with score, vrije ruimte, transformatiepotentie, gebouwinformatie, and kansen. The new design uses a completely different layout: Verdict Hero (full-width) -> 3-col Deal-Maker Grid -> Intelligence Strip -> footer button (already provided by ParcelPanelShell).

All required data is already available in `ScanResultItem`. The `score_breakdown` field contains per-factor contributions (`factors.pand_status_signal`, `factors.zoning_value`, `factors.underutilization`, etc.) and subscores (`subscores.vacancy`, `subscores.buildability`). The three Deal-Maker Grid cards need mapping logic from these existing factors to `land_potential`, `vertical_potential`, and `zoning_compatibility` concepts — this is frontend derivation only.

**Primary recommendation:** Replace `PotentieLayer.tsx` entirely with a new component. Reuse existing helpers (`deriveTransformatiePotentie`, `hasResidentialMixedBestemming`, vrije ruimte calculation) but restructure them into the new layout. No backend changes needed.

## Architecture Patterns

### Component Structure
```
frontend/src/components/map/panels/parcel/layers/
  PotentieLayer.tsx        # REPLACE ENTIRELY — new dashboard component
```

### Pattern 1: Complete Component Replacement
**What:** Delete all existing PotentieLayer content and rebuild from scratch. The existing helpers (`deriveTransformatiePotentie`, `hasResidentialMixedBestemming`, vrije ruimte calc, `formatPandStatusLabel`) should be kept but reorganized.
**When to use:** When the visual structure changes completely but the data model stays the same.

### Pattern 2: Discriminated Verdict Type
**What:** Use a typed verdict object derived from score:
```typescript
type Verdict = {
  label: string        // 'ZEER KANSRIJK' | 'MOGELIJKHEDEN' | 'BEPERKT POTENTIEEL'
  action: string       // 'GO' | 'ONDERZOEK' | 'NO-GO'
  color: string        // 'text-green-600' | 'text-amber-500' | 'text-red-500'
  badgeColor: string   // 'bg-green-500' | 'bg-amber-500' | 'bg-red-500'
  icon: ComponentType  // Check | HelpCircle | XCircle
}

function deriveVerdict(score: number | null): Verdict
```
**When to use:** Single source of truth for all verdict-related rendering.

### Pattern 3: Score Breakdown Mapping to Grid Cards
**What:** The backend `score_breakdown` structure is:
```typescript
interface ScoreBreakdown {
  factors: {
    pand_status_signal: number    // 0-40 points
    building_age: number          // 0-5 points
    zoning_value: number          // 0-20 points
    footprint_size: number        // 0-5 points
    underutilization: number      // 0-30 points
    vacancy_subscore: number      // 0-100 normalized
    buildability_subscore: number // 0-100 normalized
    vacancy_guardrail: number     // adjustment delta
  }
  subscores: {
    vacancy: number       // 0-100
    buildability: number  // 0-100
  }
  model_version: string
}
```

Map to 3 cards:
- **Card 1 (Vrije Grond)**: Derived from `vrije ruimte %` calculation (parcel area vs pand footprint). Contribution = `factors.underutilization` + `factors.footprint_size` (raw points, round to int)
- **Card 2 (Optoppotentie)**: Derived from `building_metrics` (actual vs max bouwlagen/bouwhoogte). Contribution = `factors.zoning_value` + `factors.building_age` (raw points)
- **Card 3 (Bestemming)**: Derived from `hasResidentialMixedBestemming()`. Contribution comes from `factors.zoning_value` (the bestemming component)

**Important:** The backend scoring factors don't map 1:1 to these three cards. The `zoning_value` factor combines bestemming type AND FAR/bebouwingspercentage. For contribution badges, use the raw factor values as-is and round to integers. Don't try to decompose further — the user just needs to see approximate point contributions.

### Pattern 4: Framer Motion Score Bar Animation
**What:** Animate the h-3 score bar width from 0% to score% on mount.
```typescript
const controls = useAnimationControls()
useEffect(() => {
  controls.start({ width: `${score}%` }, { duration: 1.2, ease: [0.4, 0, 0.2, 1] })
}, [score])
```
Or simpler with `useSpring` (already used in ParcelBentoOverview's AnimatedNumber):
```typescript
const spring = useSpring(0, { stiffness: 40, damping: 20 })
useEffect(() => { spring.set(score ?? 0) }, [score])
const width = useTransform(spring, v => `${v}%`)
// <motion.div style={{ width }} />
```

### Pattern 5: One-liner Template Generation
**What:** Deterministic template combining top-2 signals from available data:
```typescript
function generateOneLiner(parcel: ScanResultItem, metrics: BuildingMetrics | null): string {
  const parts: string[] = []
  // Priority order: vrije ruimte, optoppotentie, bestemming, vacancy, bouwjaar
  if (vrijePct != null) parts.push(`${vrijePct}% vrije ruimte`)
  if (lagenHeadroom > 0) parts.push(`+${lagenHeadroom} lagen headroom`)
  if (hasWonen) parts.push('Wonen-bestemming')
  if (parcel.vacancy_signal === 'leegstaand_pand') parts.push('leegstandsignaal')
  return parts.slice(0, 2).join(' \u00b7 ') || 'Beperkte data'
}
```

### Anti-Patterns to Avoid
- **Don't use BentoPod for the grid cards**: The design calls for custom `bg-white border border-slate-100 rounded-[20px]` cards, not the existing BentoPod style (`bg-white/40` without border)
- **Don't add overflow-y-auto**: The entire point is no-scroll on 1080p+. If content doesn't fit, reduce padding — never add scroll
- **Don't create click handlers on grid cards**: Locked decision — purely informational, zero interaction
- **Don't call AI for one-liners**: Template-based only. No network calls

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Spring animations | Custom requestAnimationFrame loop | `useSpring` from framer-motion | Already used in AnimatedNumber, handles edge cases |
| Score color mapping | Inline ternary chains | Typed `deriveVerdict()` function | Single source of truth, testable |
| Number formatting | `toFixed()` with manual locale | `toLocaleString('nl-NL')` | Consistent with rest of codebase |

## Common Pitfalls

### Pitfall 1: Height Budget Overflow on 1080p
**What goes wrong:** Dashboard requires scroll on 1080p screens, defeating the purpose
**Why it happens:** Panel shell has address header (~80px), category tabs (~48px), and footer (~92px) eating into available height. The content area for the dashboard is NOT the full viewport — it's roughly 620px panel height minus ~220px of chrome = ~400px available
**How to avoid:** Strict height constraints: Hero 100px max (not 140px on tight screens), Grid 130px fixed, Strip ~100px, gaps 12px instead of 16px if needed. Test at exactly 1080px viewport height
**Warning signs:** Any `overflow-y-auto` appearing on the dashboard content

### Pitfall 2: score_breakdown is null for Legacy Parcels
**What goes wrong:** Contribution badges crash or show NaN
**Why it happens:** Older scan results may have `score_breakdown: null` or a legacy format without the `factors` key
**How to avoid:** Always null-check: `parcel.score_breakdown?.factors?.underutilization ?? null`. When null, show "—" in badge instead of points
**Warning signs:** TypeScript not catching because `score_breakdown` is typed as `Record<string, unknown> | null`

### Pitfall 3: Optoppotentie Data Often Missing
**What goes wrong:** Card 2 (Optoppotentie) shows "—" for most parcels
**Why it happens:** `max_bouwlagen` coverage is ~0% (PLU WMS useless), `actual_bouwlagen` coverage is ~61%. Many parcels have neither max nor actual bouwlagen
**How to avoid:** Show "—" with "Geen data" sub-text when both max and actual are null. The card still renders in the 3-col grid (never collapse to 2-col)
**Warning signs:** Most parcels showing empty optoppotentie card

### Pitfall 4: Intelligence Strip Conditional Rendering
**What goes wrong:** Strip takes up space even when all signals are hidden, or strip disappears completely leaving a gap
**Why it happens:** All three signals are conditional: Market Friction needs `listing_duration_days > 0`, Vacancy needs `vacancy_signal` not being `in_gebruik`, Transformation needs `score > 60 AND bouwjaar < 1980`
**How to avoid:** When zero signals match, either show a single muted "Geen bijzondere signalen" bar or hide the strip and let the grid/footer spacing adjust. Prefer the former to maintain consistent height

### Pitfall 5: Score Bar Color Should Match Verdict
**What goes wrong:** Amber bar for a green GO verdict
**Why it happens:** Hardcoding `bg-aura-amber` for the score bar like the current implementation
**How to avoid:** Use the same verdict-derived color for the score bar fill: green for GO, amber for ONDERZOEK, red for NO-GO

function deriveVerdict(score: number | null) {
  if (score == null) return { label: 'ONBEKEND', action: 'ONDERZOEK', color: 'text-slate-400', badgeColor: 'bg-slate-400' }

### Vrije Grond Calculation (already exists in PotentieLayer)
```typescript
// Source: current PotentieLayer.tsx lines 117-122
const rawPandOpp = parcel.building_metrics?.pand_oppervlakte_m2 ?? null
const pandOppM2 = rawPandOpp === 0 && parcel.has_pand ? null : rawPandOpp
const vrijePct = pandOppM2 != null && parcel.area_m2 != null && parcel.area_m2 > 0
  ? Math.max(0, Math.min(100, (1 - pandOppM2 / parcel.area_m2) * 100))
  : null
const vrijeM2 = pandOppM2 != null && parcel.area_m2 != null
  ? Math.round(parcel.area_m2 - pandOppM2)
  : null
```

### Optoppotentie Headroom
```typescript
// Source: current PotentieLayer.tsx deriveTransformatiePotentie
const bm = parcel.building_metrics
const actualLagen = bm?.actual_bouwlagen ?? null
const maxLagen = bm?.max_bouwlagen ?? null
const actualHoogte = bm?.actual_bouwhoogte ?? null
const maxHoogte = bm?.max_bouwhoogte ?? null

// Prefer lagen for display (more intuitive for investors)
const lagenHeadroom = actualLagen != null && maxLagen != null && maxLagen > actualLagen
  ? maxLagen - actualLagen : null
const hoogteHeadroom = actualHoogte != null && maxHoogte != null && maxHoogte > actualHoogte
  ? Math.round(maxHoogte - actualHoogte) : null
```

### Contribution Badge Points Mapping
```typescript
// From score_breakdown.factors (raw scoring points)
const factors = (parcel.score_breakdown as any)?.factors as Record<string, number> | undefined

// Card 1 — Vrije Grond: underutilization + footprint_size
const landPts = factors
  ? Math.round((factors.underutilization ?? 0) + (factors.footprint_size ?? 0))
  : null

// Card 2 — Optoppotentie: building_age + part of zoning_value
const verticalPts = factors
  ? Math.round((factors.building_age ?? 0) + (factors.zoning_value ?? 0))
  : null

// Card 3 — Bestemming: zoning_value (already counted above, so use subscore instead)
// Alternative: use buildability_subscore scaled down
const zoningPts = factors
  ? Math.round(factors.zoning_value ?? 0)
  : null
```

**Note on double-counting:** `zoning_value` appears in both Card 2 and Card 3 mapping because the backend factor combines vertical potential AND bestemming type. For the contribution badges, this is acceptable — they show "which scoring factor powered this card" not "unique non-overlapping point allocation." The total of badge points will NOT equal the total score, and that's fine — badges are transparency signals, not an accounting ledger.

## Open Questions

1. **Contribution badge point sum vs total score**
   - What we know: Backend factors sum to raw points that get normalized/weighted. Badge points (raw factor values) won't add up to the total score
   - What's unclear: Whether users will be confused by this mismatch
   - Recommendation: Accept the mismatch. Badges show "+N pts" per factor, not "N/100". The total score is independently displayed in the hero. Users care about relative magnitude ("this factor contributed a lot") not arithmetic consistency

2. **Optoppotentie display when only hoogte data exists (no lagen)**
   - What we know: `actual_bouwlagen` coverage is 61%, `max_bouwlagen` is ~0%. `actual_bouwhoogte` may be available from 3D BAG
   - What's unclear: Whether to show hoogte headroom in meters when lagen headroom is unavailable
   - Recommendation: Show hoogte headroom as fallback: "+Nm headroom" when lagen unavailable. Show "Geen data" only when neither exists

3. **Intelligence strip with zero matching signals**
   - What we know: All 3 signals are conditional. Many parcels (especially "in_gebruik") may have zero signals
   - What's unclear: Whether to show empty strip or hide it
   - Recommendation: Show a single muted bar "Geen bijzondere signalen gedetecteerd" to maintain consistent height budget
