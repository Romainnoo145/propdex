```typescript
export async function markChangeRead(changeId: string, accessToken: string | null): Promise<void> {
  await apiFetch(`${MONITORING_BASE}/changes/${changeId}/read`, {
    accessToken,
    method: 'POST',
  })
}

export async function markChangeUnread(changeId: string, accessToken: string | null): Promise<void> {
  await apiFetch(`${MONITORING_BASE}/changes/${changeId}/read`, {
    accessToken,
    method: 'DELETE',
  })
}

export async function markAllChangesRead(
  accessToken: string | null,
  projectId?: string
): Promise<MarkAllReadResponse> {
  const params = projectId ? `?project_id=${projectId}` : ''
  return apiFetch<MarkAllReadResponse>(`${MONITORING_BASE}/changes/read-all${params}`, {
    accessToken,
    method: 'POST',
  })
}
```

**3. Add to `frontend/src/hooks/useNotifications.ts`:**

a) `useMarkChangeRead()` mutation:
- mutationFn: calls `markChangeRead(changeId, accessToken)`
- onMutate (optimistic): Update the `['changes', ...]` query cache to add changeId to a local read set. Also decrement the `['notifications', 'unread']` count optimistically.
- onSuccess: Invalidate `['notifications', 'unread']` to get fresh server counts
- onError: Roll back optimistic update

b) `useMarkAllRead(projectId?: string)` mutation:
- mutationFn: calls `markAllChangesRead(accessToken, projectId)`
- onSuccess: Invalidate `['notifications', 'unread']` and all `['changes', ...]` queries
- No optimistic update needed (full invalidation is fine for bulk action)

c) `useReadChangeIds(projectId?: string)` — NEW query hook:
- Fetches the list of change IDs the current user has read (for the current view scope)
- This can be derived from an enhanced changes endpoint OR a separate lightweight endpoint
- SIMPLEST APPROACH: Add `read_change_ids` field to the ChangeRecordListResponse from the backend (Plan 49-01 already provides the data). If that's not available, track read IDs client-side via mutation cache updates.
- RECOMMENDED: Use a client-side Set maintained via mutation cache. When useAllChanges or useProjectChanges loads, ALL changes start as "server-defined read state" (the backend doesn't include read_change_ids yet). Instead, use the existing `/api/monitoring/unread` per-project counts to derive initial state, and let mutations update a local TanStack Query cache key `['read-ids']` that the components check.
- ACTUALLY SIMPLEST: The backend's GET /changes endpoint should return a `read_change_ids` list alongside `changes`. Update Plan 49-01's router to include this. BUT since Plan 49-01 is already finalized, use this approach instead:
  - Add a new query `useReadChangeIds()` that calls a new lightweight endpoint: `GET /api/monitoring/read-ids?project_id=X` returning `{ read_ids: string[] }`. This endpoint queries change_read_states for the current user and returns all change_id values.
  - If adding a new endpoint feels like scope creep for Plan 02, the alternative is: modify the existing `fetchAllChanges` / `fetchProjectChanges` API functions to also call the read-ids endpoint in parallel and merge the results. The useAllChanges / useProjectChanges hooks can be composed with useReadChangeIds.

DECISION: The cleanest approach is to NOT add a new endpoint but instead **include read_change_ids in the ChangeRecordListResponse** from the backend. Add this as an enhancement to the GET /changes endpoint in Plan 49-01's Task 2 (it's a minor addition — query change_read_states WHERE user_id = current_user.id AND change_id IN (...change_ids) and include the result). Since Plan 49-01 runs first (wave 1), this is safe.
