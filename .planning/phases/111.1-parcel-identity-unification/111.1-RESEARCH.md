# Phase 111.1: Parcel Identity Unification - Research

**Researched:** 2026-03-16
**Domain:** Database schema migration, identifier normalization, SQLAlchemy 2.x Alembic
**Confidence:** HIGH

---

## Summary

There are three identifier namespaces in the codebase that currently cannot be joined to each other reliably. `parcel_cache.parcel_id` stores the BRK numeric object identificatie (e.g., `"0983100000006658"`). `parcel_favorites.parcel_id` stores the PDOK human-readable display string (e.g., `"Venlo I 6658"`). `parcel_documents.parcel_id` stores the ParcelCache UUID as a plain VARCHAR string (not a typed FK).

The goal of this phase is to add a `parcel_code` column to `parcel_cache` that stores the PDOK display string, backfill it from the PDOK Kadaster API for all 137k existing rows, and then add a typed FK from `parcel_favorites` pointing to `parcel_cache` so queries can join favorites to geometry, address, and enrichment data. `parcel_documents.parcel_id` already points at `parcel_cache.id` (UUID), so adding a FK constraint there is a separate, smaller concern.

**Primary recommendation:** Add `parcel_code VARCHAR(50) NULLABLE` to `parcel_cache`, backfill via PDOK WFS using `identificatie` → `kadastrale_gemeente_waarde + sectie + perceelnummer`, then add `parcel_cache_id UUID FK NULLABLE` to `parcel_favorites`. Do NOT change the existing `parcel_favorites.parcel_id` string — it is the stable Kadaster display key used everywhere in API routes.

## Architecture Patterns

### Recommended Changes

#### 1. `parcel_cache` — new column
```python
# In parcel_cache.py model
parcel_code: Mapped[str | None] = mapped_column(
    String(50), nullable=True, index=True,
    comment="PDOK human-readable display string (e.g. 'Venlo I 6658')",
)
```

Alembic migration adds:
- `parcel_code VARCHAR(50) NULLABLE`
- Index on `(organization_id, parcel_code)`
- UniqueConstraint on `(organization_id, parcel_code)` — after backfill confirms uniqueness

#### 2. `parcel_favorites` — new FK column (ADDITIVE, keeps existing `parcel_id`)
```python
# In parcel_favorite.py model — ADD alongside existing parcel_id string field
parcel_cache_id: Mapped[uuid.UUID | None] = mapped_column(
    ForeignKey("parcel_cache.id", ondelete="SET NULL"),
    nullable=True,
    index=True,
    comment="FK to parcel_cache.id — populated after parcel_code unification",
)
```

This approach preserves the existing `parcel_id` string (used as URL parameter in all routes) while adding a joinable FK.

#### 3. `parcel_documents` — add FK constraint only
The column already stores correct UUID values matching `parcel_cache.id`. Just add a FK constraint in Alembic:
```sql
ALTER TABLE parcel_documents
  ADD CONSTRAINT fk_parcel_documents_parcel_cache
  FOREIGN KEY (parcel_id) REFERENCES parcel_cache(id) ON DELETE CASCADE;
```
This requires changing `parcel_id` column type from VARCHAR to UUID first (or keeping as VARCHAR with a check). Since data is already UUID strings, a cast migration is cleaner.

**Alternative (simpler):** Add a separate `parcel_cache_id UUID FK` column to `parcel_documents` (same additive pattern as favorites). Avoids type migration risk.

#### 4. Backfill Tool
The backfill must:
1. Query all `parcel_cache` rows where `parcel_code IS NULL`
2. For each row, call PDOK WFS with the `parcel_id` (BRK identificatie)
3. Extract `kadastrale_gemeente_waarde + sectie + perceelnummer` from response
4. UPDATE `parcel_cache.parcel_code` with the display string
5. Then UPDATE `parcel_favorites.parcel_cache_id` by joining on `parcel_code = parcel_favorites.parcel_id`

**Batching:** Use semaphore(10) pattern from area_scan.py — 10 concurrent PDOK requests max.

### PDOK WFS: Numeric identificatie → Display Format

The `parcel_cache.parcel_id` stores values like `"0983100000006658"`. The PDOK WFS `identificatie` parameter accepts this directly. The response includes `kadastrale_gemeente_waarde` (e.g., `"Venlo"`), `sectie` (e.g., `"I"`), and `perceelnummer` (e.g., `6658`).

Display string composition (matches existing `scans/router.py` lines 305-308):
```python
parcel_code = f"{kadastrale_gemeente_waarde.strip()} {sectie.strip()} {perceelnummer}"
```

**CRITICAL NOTE:** The `parcel_cache.parcel_id` may be a pre-WFS fallback format for some rows (e.g., `"HTT02-A-1234"` dash-separated format). The backfill must handle rows that already have a non-numeric format — skip PDOK lookup, use as-is for `parcel_code`.

Observed data shows all 137k Venlo rows use the pure numeric format (`"0983100000006658"`). Other municipalities may differ.

### Existing Code Pattern to Follow

`area_scan.py` handles the PDOK lookup pattern. The scan worker already calls `_upsert_parcel_cache` at scan time — but it stores the `identificatie` only, not the display string. The display string derivation happens on-demand in `scans/router.py` via `_resolve_pdok_cadastral_parcel_at_rd`.

**Option A (preferred):** Backfill `parcel_code` via batch PDOK WFS lookups
**Option B:** Derive `parcel_code` at scan time by adding it to `_upsert_parcel_cache` (also needed to fix going-forward, but backfill still needed for existing rows)

Both are required. The plan should include both.

## Common Pitfalls

### Pitfall 1: Uniqueness of parcel_code per organization
**What goes wrong:** Two organizations scanning the same municipality get the same `parcel_code` values in their respective `parcel_cache` rows (separate rows due to multi-tenant isolation). A UNIQUE constraint on `parcel_code` alone would fail. Must be `UNIQUE(organization_id, parcel_code)`.

**How to avoid:** UniqueConstraint uses both columns, as done for `parcel_id`.

### Pitfall 2: parcel_favorites join using wrong side of the identifier
**What goes wrong:** Joining `parcel_favorites.parcel_id` (display string like `"Venlo I 6658"`) to `parcel_cache.parcel_id` (numeric `"0983100000006658"`) — no match exists, returns 0 rows silently.

**How to avoid:** The join must use `parcel_favorites.parcel_id = parcel_cache.parcel_code` (new column), NOT `parcel_cache.parcel_id`.

### Pitfall 3: parcel_documents FK type mismatch
**What goes wrong:** `parcel_documents.parcel_id` is VARCHAR(50) storing UUID strings. Adding a FK to `parcel_cache.id` (UUID type) requires a type cast or column type change. PostgreSQL will reject the FK if types don't match.

**How to avoid:** Either (a) change `parcel_documents.parcel_id` to UUID type with `USING parcel_id::uuid` cast in Alembic, or (b) add a separate `parcel_cache_id UUID FK` column and populate it from the existing string values. Option (b) is safer (no data loss risk).

### Pitfall 4: PDOK WFS rate limits during backfill
**What goes wrong:** Firing 137k sequential requests exhausts PDOK rate limits and gets the IP blocked.

**How to avoid:** Use asyncio.Semaphore(10) + batch processing (100 rows per batch) + short sleep between batches. Follow the `area_scan.py` pattern exactly.

### Pitfall 5: Backfill null coverage — PDOK may not return all identifiers
**What goes wrong:** Some `parcel_cache` rows were created from fallback identifier formats (non-numeric). PDOK WFS lookup by identificatie may return no match. `parcel_code` remains NULL for those rows.

**How to avoid:** Log nulls, do not fail — `parcel_code` is NULLABLE intentionally. Downstream join uses LEFT JOIN (not INNER JOIN).

### Pitfall 6: Adding the scan-time path without backfilling
**What goes wrong:** New scans populate `parcel_code` going forward, but existing 137k rows remain NULL. Portfolio queries that join on `parcel_code` return no data for existing favorites.

**How to avoid:** Plan MUST include a backfill step that runs before any FK-dependent queries go live.

### Pitfall 7: Transaction already begun
**What goes wrong:** Using `async with db.begin()` in the backfill tool causes `InvalidRequestError: A transaction is already begun on this Session`.

**How to avoid:** Use `db.add() / db.flush() / db.commit()` pattern per MEMORY.md. The backfill tool should use direct commits per batch, not nested transaction context managers.

## Scope Clarification

The objective mentions:
1. Add `parcel_code` to `parcel_cache` — the PDOK display string. **IN SCOPE.**
2. Backfill existing parcels. **IN SCOPE.**
3. Add FK from `parcel_favorites` to `parcel_cache`. **IN SCOPE** — best done as nullable `parcel_cache_id` UUID FK column (additive).
4. Add FK from `parcel_documents` to `parcel_cache`. **IN SCOPE** — but data shows `parcel_documents.parcel_id` already stores `parcel_cache.id` as UUID string. Adding a typed FK is a constraint addition. Safe additive column approach recommended.
5. Enrichment queries via joins (`address`, `gemeente_naam`, `wijk_naam`). **PARTIALLY IN SCOPE** — `address` and `gemeente_code` are in `parcel_cache`. `gemeente_naam` and `wijk_naam` are denormalized in `parcel_favorites` itself (stored at write time). No additional join needed for those.

## Migration Sequencing

The three database changes must be sequenced:

1. **Migration A**: Add `parcel_cache.parcel_code` (nullable, no constraints yet)
2. **Migration B**: Add `parcel_favorites.parcel_cache_id` (nullable FK)
3. **Migration C**: Add `parcel_documents` FK (separate migration)
4. **Backfill step**: Populate `parcel_cache.parcel_code` from PDOK
5. **Backfill step**: Populate `parcel_favorites.parcel_cache_id` by joining on `parcel_code = parcel_id`
6. **Optional Migration D**: Add UniqueConstraint on `(org_id, parcel_code)` after verifying nulls

Migrations A+B+C can be in a single Alembic revision. The backfill tool runs separately (CLI script, like existing backfill tools).

---

## Going-Forward Path (scan time)

After backfill, new scans should populate `parcel_code` at write time so no backfill is needed for new parcels. The `_upsert_parcel_cache` function in `area_scan.py` needs a `parcel_code` parameter. However, deriving the display string from a PDOK WFS call at scan time adds latency. Two options:

- **Option A (deferred):** Continue deriving on-demand via `_resolve_pdok_cadastral_parcel_at_rd` at map click time, save to cache. Add a `parcel_cache.parcel_code = pdok_result` update at first resolve.
- **Option B (preferred for integrity):** Pass the PDOK properties through to `_upsert_parcel_cache` — the scan already fetches PDOK data, just save the display string while there.

Option B requires touching `area_scan.py`. It's cleaner and avoids a second wave of backfill as new parcels are scanned. The plan should include this.

## Open Questions

1. **Uniqueness of PDOK display string**
   - What we know: Within a municipality, `kadastrale_gemeente + sectie + perceelnummer` is unique per parcel
   - What's unclear: Across municipalities, two parcels with the same sectie+perceelnummer but different gemeente names might appear the same if the gemeente name is ambiguous
   - Recommendation: UniqueConstraint on `(organization_id, parcel_code)` is safe because multi-tenant. Confirm after backfill.

2. **PDOK WFS coverage for all 137k rows**
   - What we know: All Venlo rows use numeric identificatie format; PDOK WFS accepts this
   - What's unclear: A small fraction may use dash-format fallback IDs — PDOK WFS won't find these by identificatie search
   - Recommendation: Log non-matches, leave `parcel_code` NULL for those rows. Future scan will populate via on-demand resolution.

3. **parcel_documents column type change risk**
   - What we know: Current 2 rows both contain valid UUID strings
   - What's unclear: Whether application code ever writes non-UUID strings to this column
   - Recommendation: Read `parcel_documents` usage in router before deciding cast vs additive column approach
