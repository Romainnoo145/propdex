# M050.5+: Real per-project-type scoring differentiation

**Captured:** 2026-05-26
**Slice context:** M052/S01 follow-up (after user UAT of score-profile presets)
**Status:** Pending — sized for M050.5 (Feature Tiering) or a dedicated slice
**Linked memory:** [[project_propdex_projecttype_lens]] · [[feedback_iron_rule_regression_pattern]]

## Problem

The frontend `/instellingen/score` UI now offers 5 project-type startprofielen
(Nieuwbouw / Transformatie / Optoppen / Splitsen / Commercieel → wonen) and
the per-parcel picker writes `project_type` via `PUT /api/parcels/{id}/project-type`,
which triggers a rescore.

**But the scoring engine only meaningfully differentiates 2 of those 5 types.**

Per `backend/app/services/score_v3.py` (M047 FACTOR_REGISTRY), only 3 factors
carry `weight_by_projecttype` overrides, and those overrides cover only
`optoppen` (3 factors) and `nieuwbouw_wonen` (2 factors):

| Factor | optoppen | nieuwbouw_wonen | other types |
|---|---|---|---|
| vrije_grond (default 13) | 12 | default | default |
| optoppotentie (default 11) | 16 | 7 | default |
| woonvisie_match (default 12) | default | 16 | default |

For `transformatie_wonen`, `splitsen`, `commercieel_naar_wonen`: **zero
shifts.** A parcel saved as Transformatie scores identically to one saved
as Onbepaald with the same org weights.

User noticed this gap during M052/S01 UAT (2026-05-26): *"Nu heb je alleen
het rijtje veranderd, maar de daadwerkelijke scoringsberekening erachter
niet toch?"* — correct.

## Why this hits now

M052/S01 wired the picker + the rescore trigger + made the project-type
chip visible on Opgeslagen cards. Users will assume the score "knows" what
project-type they picked. For 3 of 5 types, it doesn't.

Currently fine as MVP-honesty (chip = intent label) but breaks expectation
once orgs configure their startprofiel.

## Scope estimate

Three new conditional-weight blocks to add:

- `transformatie_wonen`: leegstand ↑, bestemming ↑, bestemmingswijziging ↓-risk-side,
  constructieve_staat ↑-risk, asbest ↑-risk
- `splitsen`: vergunning_succeskans ↑↑, perceelgrootte ↑, bestemmingswijziging ↑-risk,
  constructieve_staat ↑-risk
- `commercieel_naar_wonen`: bestemming ↑↑, leegstand ↑↑, bestemmingswijziging ↑↑-risk,
  bodemverontreiniging ↑-risk

Likely 5-8 factor entries per type need `weight_by_projecttype` extension.

Plus: `potentie_risico_balance` per type is already in the deferred bucket
(per memory `weights-principes-20260420.md`: nieuwbouw 0.7 / transformatie 0.5
/ optoppen 0.4). Same slice should land both.

## Constraints

- M047 weights are LOCKED via assertion at module load (`_REGISTRY_POTENTIE_SUM == 100`
  and per-type sum-guards in `_ALL_PROJECT_TYPES`). New overrides must keep
  category sums at 100.
- Iron-rule regression pattern (per memory `feedback_iron_rule_regression_pattern`):
  encode the existing optoppen + nieuwbouw_wonen weight values as regression tests
  in `backend/tests/regression/` BEFORE adding new types — protects against
  accidental shift.
- Smoke-test pattern from M048/Phase 6 (≥0.2 score-differentiation between wijken
  per project_type) should extend to the 3 new types.

## Acceptance criteria

1. `FACTOR_REGISTRY` carries explicit `weight_by_projecttype` for all 5
   non-onbepaald types (`nieuwbouw_wonen`, `transformatie_wonen`, `optoppen`,
   `splitsen`, `commercieel_naar_wonen`) on a defined subset of factors.
2. `_ALL_PROJECT_TYPES` sum-guards pass for every type.
3. Regression test pins the M047-locked weights (optoppen 3-factor shifts +
   nieuwbouw_wonen 2-factor shifts).
4. Smoke-test asserts score-differentiation between two wijken for each of
   the 3 new types (transformatie/splitsen/commercieel) — same pattern as
   the existing nieuwbouw_wonen smoke-test.
5. Frontend `PRESETS` weights in `scoreWeights.ts` re-derived from backend
   registry — ideally via a new `GET /api/scoring/presets` endpoint so it's
   no longer a hand-maintained duplicate (or: explicit code-comment linking
   the values).
6. Settings UI shows a clear hint per preset that the weights are "starting
   defaults — adjust below" so users understand the layering of org weights
   + per-type conditional shifts.

## Estimated effort

- Research: 2-3h (per-factor design per new type, validate with real-data
  smoke-test results)
- Implementation: 3-4h backend (registry + tests + smoke), 1h frontend
  (preset sync or endpoint)
- Verification: 1h

Total: ~1 day. Fits cleanly in M050.5 alongside the existing
`potentie_risico_balance per type` deferred-item, since both need the same
per-type design judgment.

  before locking weights.
